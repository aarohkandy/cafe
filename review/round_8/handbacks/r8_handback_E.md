### M-29 residual: the store's longitude and the coverage test now agree on every accepted box
- Cause. The store was written with `lon mod 360` (`_sub` end, `_std`), `box360` accepts a box that does not cross 0 E (w in [0, 360), w + span <= 360), and `_ocean_cached` compares the store's lon with that box. A coarse grid next to 0 E needs the bracketing neighbour across the seam (box 0.3 to 0.8 E on a 1 deg grid: 359.5, 0.5, 1.5; box ending at 359.95: 359.5, 0.5 as the east neighbour). Mod 360 puts that neighbour at the far end of the axis: `_std` sorts it into a hole (0.5, 1.5, 359.5), the check sees `lon.min() = 0.5 > w + 0.1`, fails, and the advice (ingest again) wrote the same store. Not only the west side: the east side of 0 E had the same defect, and before M-29 too.
- Fix (root cause: one frame). A lab store's lon axis is in the frame of the box (`box360`'s west and east): the nearest image of each file longitude to the box centre, so the axis is continuous, the neighbour across 0 E is below 0 (-0.5) or above 360 (360.5) and never wrapped into a hole; for every box that does not touch 0 E the values are identical to before (the dateline case, 179.84 ... 180.48 from files in -180..180 or in 0..360, gives the same coordinates after `_std`'s 5-decimal rounding; the existing round-trip tests against the GOFS truth pass unchanged). `_ocean_cached` is unchanged: it compares in the same frame by construction.
  - `conventions.wrap_about(deg, centre)` (new, 3 lines): `deg` moved by a multiple of 360 to the image nearest `centre`; exact (a value within 180 of the centre is returned unchanged).
  - `hycom._sub`: wraps the file's lon with it about the box centre, cuts in that frame (`_cut` loses its `x` argument: positions and edges are in one frame now) and no longer mods the result. `hycom._std(ds, wrap=True)`: `wrap` False keeps the lon as given; `ingest_lab_hycom` passes `wrap=False`, the GOFS assembly and all other callers keep mod 360. Store attribute `lon_convention` now reads "0..360 degrees east (continuous with the box where it touches 0 E)" (still starts with `0..360`).
  - `hycom.read_archv`: the 0.5 deg pre-cut used `lon < w - 0.5 -> +360` and a fixed 0.5 deg window, so an archv grid coarser than about 0.4 deg left `_sub` no neighbour to keep (the same loop for archv) and a neighbour across 0 E was dropped. It now takes the window as before OR `_cut`'s bracket, in the box frame. Fine grids select exactly what they did.
- Every reader of the store's lon, checked (callers of `hycom.open_store`, `Ocean`, `Bathymetry`; grep `\.lon`, `wrap360`, `axes[3]`):
  - `Ocean.inside`, `Ocean._at` (so current, density, sound_speed, temperature): took the query mod 360, which for an axis of -0.5 .. 1.5 called 359.9 outside and a query at 360.35 fine only by luck. New `Ocean._lon`: `wrap_about(lon, axis middle)`. For an axis inside [0, 360) the in-axis answers are identical to `wrap360` (an in-axis position has exactly one image within 180 of the middle); only which edge `interp` holds for a query far outside can differ, and `inside` flags those.
  - `Ocean.bounds` (maps with `wrap360(x + 180) - 180`): correct for any x, unchanged.
