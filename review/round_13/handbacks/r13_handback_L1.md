## 6. The CDF-1 parser is not bounded by MAX_ITEM in its counts (M-15)

Code. `remote.MAX_ENTRIES = 65536`; `_Buf.count(most=None)` raises the damaged-header ValueError for a count above `most`, and `_Buf.kind` (dimension, attribute and variable lists) and the rank count of a variable pass it. NetCDF's own limits are 1024 to 8192. A hostile 2**31 - 1 is refused at once, having fetched only the first 64 kB, where it read the file to its end (4 MB: 1.0 s and 43 MB; linear in file size) into lists. The per-field cap `MAX_ITEM` is unchanged; the real restart header and the real files have a few dozen entries.
DECISIONS row text: "`remote.parse_cdf1` bounds the number of entries a header promises: a list of dimensions, attributes or variables, or the dimension ids of one variable, may hold at most `MAX_ENTRIES` (65536; NetCDF's own limits are 1024 to 8192), else the header is damaged (ValueError). M-15 bounded one field's size (`MAX_ITEM`) and a count's sign but not how many entries a count promises, so a count of 2**31 - 1 on a big file with bytes behind it was read to the end of the file into lists (about 11 MB of memory per MB of file; the 2.4 GB UMWM restart would have needed about 25 GB) before the EOFError. Amends the M-15 row."
CHANGELOG line: "A NetCDF header whose list count is absurd is refused at once (ValueError) instead of reading the whole file into memory (R13 look-ahead L1, M-15)."
Test: `tests/test_remote.py::test_r13_l1_a_hostile_entry_count_is_refused_at_once_not_after_reading_the_file` (dimensions, attributes, variables, the ids of a variable: a ValueError, under 1 MB fetched from a 4 MB file; a header at the cap is accepted).
