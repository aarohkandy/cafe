## 1. What runs

`bin/run_premission` is `python -m cafe.pm run`. One command takes the two orca files plus the ocean source to `report/index.html`, `report.json` and `credibility.html`, with a sha256
ledger per stage, resume, and a chained audit. The q2 quick run of 2026-10-31 on homebase did it end to end; the eight compute stages took 691.9 s and its cold ingest 522 s (a warm ingest takes about 6 s, so a warm quick
run is about 700 s of the 1200 s limit; the planner's stage-1 estimate was 2.5 times high until `make bench` was rerun on 2026-11-01; with the new costs the q5 plan was 2.05 times low, 52.68 s against 108 s for 64 members, so the estimate is now called a lower bound, DECISIONS 288; the ratio is per machine: q9 on the 32-vCPU burst VM, with homebase's rates, ran stage 1 at 4.2 times its plan, DECISIONS 468).

| Stage | What it does | State |
|---|---|---|
| ingest | byte-range reads of orca WRF, UMWM and restart spectra, GOFS 3.1, TAO/TRITON, GEBCO into Zarr, schema-checked | runs; offline once cached (`CAFE_OFFLINE=1`) |
| hangar | provenance check of the platform files, baseline model coefficients (no Hangar CFD run) | runs |
| stage 1 | ensemble (Latin hypercube; n_max 16 (ci), 64 (quick), 256 (4h), 512 (overnight), n_min 8, 32, 73, 73; ci and quick cannot certify P(fail) < 5 %, DECISIONS 69, 70) of glider, USV, UAS and the RF, acoustic and Iridium links; Wilson intervals; sequential stopper; failure modes; sensitivities | runs |
| windows, stage 3 | LES windows (native JAX lattice kernel), FEA of the glider hull, free-surface hull window (OpenFOAM interFoam) | LES windows are not run with `--gpus 0` (above; `ci` keeps one smoke window); the free-surface hull window runs where it fits; no GPU path has ever run |
| refit | pools passed windows into drag multipliers | never fires on CPU (no window passes); a single pass, not the loop of BRIEF 2.6 |
| stage 1b | stage 1 rerun with refitted multipliers (or with the run's own sub-grid calibration), else a copy; USV brief-prior sensitivity case | runs |
| emulator | Kriging per vehicle class, flip search of single changes | trains only with 100 distinct points per emulator scope (vehicle class, platform, window length; DECISIONS 535), which one run does not make; the flip search falls back to Stage 1 |
| report | `report.json` as the source of truth, HTML from it, credibility report (NASA-STD-7009B, ASME V&V 20, assumed inputs), reach map | runs |

2-worker batch peaks at 12.5 GB for the whole container, about 25 GB before).

**Memory model of stage 1 (review round 5, M-6, DECISIONS 281; changed in round 6, M-2, DECISIONS 309).** The worker count is the CPUs or what the memory holds, the smaller: `budget.plan` takes the
memory limit (`par.memory_gb()`: the cgroup limit, else the host's available memory), the environment (`ENV_GB_PER_DEG2_DAY` 0.0031 GB per deg^2 of the padded box per window day,
9.0 GB for the 6-day demo, or the size on disk of every Zarr store of the cache and the ocean store if larger; the plan is made again when the ingest ends) and `WORKER_GB` 0.9 per worker (0.81 to 0.84 GB measured, before the real environment), and writes
`workers_by_cpu`, `workers_by_memory` and `workers` into `plan.json`. It refuses a mission for which not even one worker fits (exit 2) and notes the memory an
explicit `CAFE_WORKERS` needs. The demo on 8 CPUs and 28 GB plans 8 workers (`workers_by_memory` 23); it is capped below 8 only under about 16 GB and refused
under about 10 GB. **Not measured (review round 7, M-38: about 15 days of the demo mission with its shipped `pad_deg` 2.0 fit 32 GB, about 10 with the default pad (round 10, M-34), and the refusal says its figure is the model's):** a real 30-day or memory-capped run, and the growth with the box's area: 9 GB is measured at one box and window (rows 267 and 270), and the model is linear in area
and days from that one point, so for another box it is a floor and not a measurement. `par._share` now stops with a named error when `/dev/shm` fills.
