# Why the demo numbers moved at round 10 (trace of q10 against a run on 6c1fde7)

Run: `/data/runs/q10lb` on orca, code `6c1fde7`, `--budget quick --gpus 0`, `PM_CPUS=6 PM_MEM=16g`, started 2026-11-07 03:52 UTC, `rc=0`, report 04:08. Orca load 0.5 before the start. It is kept. Reference: `/data/runs/q10` (code `8b870a6`, read only). Verdicts of all 4 vehicles and 4 links are unchanged; ledger checks all ok; `audit /data/runs/q10lb --ledgers-only`: 0 problems; `traceability_problems` empty.

## 1. The TAO cache was empty under `tao/s2`: one online fetch

The ledger note says so: "cold fetch: the TAO/TRITON moorings for the box and window ... this code fills /data/tao/s2: one run with network access, 202 s (the network step; --budget does not count it)". 15 moorings, `tao/s2` is 148 MB. Stage times: ingest 340 s (the 202 s fetch, the rest the derived surface layer), stage 1 148 s, stage 1b 54 s, emulator 380 s, report 24 s.

## 2. Why the mooring count went from 11 to 14: the data, not the code

The three added moorings are **T5N180W, T5S165E, T5S170W**. NOAA published delayed-mode (D) files for them after q10's cache was built.

Evidence:

- q10's cache was fetched on 2026-10-29. For these three moorings (and T5N170W) the files with that date are the real-time (R) files only (R_AIRT, R_RH, R_SST, R_WIND). Every other mooring has D and R files of that date. `fetch_tao` downloads every candidate of every mode, so a D file that the catalog listed would be there.
- The D files of the four are dated 2026-11-06 15:47 on disk (the d5f4fa3 demo downloaded them), and their own NetCDF attribute `date_created` is 2026-11-05T16:36Z to 16:39Z: created after q10's fetch.
- The R files of these moorings have QC flag 3 for the whole window (865 samples each, none good under `GOOD["R"] = (1, 2)`). In fact every R wind file in the box is flag 3 in the window. So with only R files a mooring has 0 usable samples and has no wind in `load_tao`; with the D file (flag 5) it has 145 hourly values.
- T5N170W also got a D file on 5 Nov, but its flags are all 9 (missing) in the window, so it still has no wind (14 of 15 moorings).
- The selection rule is not the cause (the verifier was right): the D and R files of one pair carry the same date in their names, so the old one-window rule would have taken them too. The catalog did not have the D files on 29 Oct.
- The fit code is not the cause. Experiment: `pipeline._wind_residuals` and `fit_wind_error` of 6c1fde7 on the current `tao/` cache with the three moorings left out give wind_speed_bias mean -0.6099, sd 0.1099, hi95 0.4609, noise 1.2835, tau 6.408 h, direction mean 7.2126, sd 2.6299: all ten numbers of q10's `priors_fitted.json` (a script run on orca through `bin/pmx.sh`). With all 14 the same code gives -0.4290 / 0.5364, the d5f4fa3 demo's numbers.
- Per-mooring numbers of `tao_compare.json` are bit-identical between q10 and q10lb for the 10 moorings in both, except T5S180W (see 3).

q10's own manifest (sha `35a37c8c...`, hashed in its ledger) is gone: the d5f4fa3 demo rewrote `tao/manifest.json` in place (selection 2, sha `1bb08d3c...`) before L0's fix existed. The above is therefore proved from file dates, QC flags and the reproduction of the priors, not from q10's manifest.

### Was the old fit wrong?

It was not wrong about its own data, and the moorings were not dropped by code: on 29 Oct three moorings had no QC-good wind. But it was incomplete, and one number was much too small: the persistent wind-speed sd, **0.110 m/s (hi95 0.461)**, against 0.569 (hi95 0.957) with 14 moorings, 5 times larger; direction sd 2.63 deg against 5.25 deg. The old value was the "estimated as 0, only the uncertainty of the mean of 11" boundary case (CREDIBILITY L19). It is a property of 6 days and 11 to 14 moorings, and one mooring decides it: with T5S165E left out (13 moorings) sd is 0.155. Nothing in the run says which moorings were excluded (prediction 2).

## 3. A second data change between the lead's d5f4fa3 demo and q10lb

T5S180W's three D files (AIRT, RH, WIND) were regenerated by NOAA (new `date_created` 2026-11-05T16:39:42Z; the old file was 2024-08-16). Online `tao/s2` has the new files, the `tao/` cache of the d5f4fa3 demo has the old ones (the manifest hashes differ in exactly these three entries, nothing else). Wind speed in the new file is about 8 % lower (median ratio 0.92), direction identical; T5S180W speed bias 0.581 to 1.116.

This explains the difference between the lead's numbers and these: priors -0.429 / 0.536 (old file) against -0.469 / 0.569 (new file); k_fail 19 / 61 / 57 against 18 / 62 / 55, on identical code. Check: pooled bias (1492 x 0.61 - 145 x 0.574) / 1927 = 0.429 for the old file, and 0.469 for the new, as the files give.

## 6. Could a real run now fail a new gate?

No gate failed in q10lb. By reading the code: M-2 cannot newly fail a series (the batch means are sample running means at the block ends, so the new deviation is at most the old one, except for rounding of unequal blocks); it is less strict by design (a 4.5 to 5 % ramp over the last third fails before, passes now; DECISIONS 536 says so). M-8 refuses only a box that pads beyond 90 deg or a full circle; the demo (34 deg wide, +-7) and the CI fixture pass. M-17 bounds `stw_cap_ms` at 3.5; the shipped platform has 3.3.

## 7. Side effects on orca

- q10lb added 28 rows to the shared emulator table (that is what the run does).
- q10 and oq9 no longer audit: `input /data/tao/manifest.json changed` (the d5f4fa3 demo rewrote it) and `derived.zarr changed` (rebuilt for each code digest; q10lb is now the one that hashes the current store and will fail the same way after the next code edit).
