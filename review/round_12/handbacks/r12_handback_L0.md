## M-35 (three findings, one cause): stored CFD and SITL results can never be stamped
- Change: `cfd.main(argv)` (was the `__main__` body) writes `cafe.receipts.stamp(r)`; the README path (`WORKDIR` = `runs/t1`, `w1`, `s1`) is the path `cfd_receipts` reads. `cafe.receipts.stamp(rec, later=False)`, new `stamp_file(path)` and `python -m cafe.receipts stamp FILE...`: stamp a result somebody has checked, atomically, with `stamped_later: true`; `stored()` shows ", stamped afterwards, not by the run" and its context rows now name the command. crosscheck.json has no writer in the repo (nothing was added: it needs an SITL run); `stamp` is its way.

- Callers checked: `stored` (cfd_receipts x3, crosscheck_receipts), `cafe.pm.receipts._app` (unchanged), `_site_data.py:148` reads suboff.incidence.json directly and does not care about the extra keys. `app_digest() == pm.receipts.code_digest("app")` test still holds.
- DECISIONS row: "A stored CFD or SITL result is read back as a receipt only with date, host, git_sha and a code_digest equal to the digest of cafe/*.py. `python -m cafe.cfd` writes its result through `cafe.receipts.stamp`; a result made before the stamp existed, or one with no writer here (runs/crosscheck.json), is stamped by `python -m cafe.receipts stamp FILE` after somebody has checked it, and carries `stamped_later`, which the row's source says. The digest covers every cafe/*.py, so an edit to any makes a stored result stale. Tests: `tests/test_receipts.py::test_r12_l0_m35_*`." Why: "Look-ahead L0 after round 12, M-35. Batch A made the reader require a stamp and no writer added one, so no real stored result could count. Amends the M-35 row."
- CHANGELOG: "`python -m cafe.cfd` stamps the result it writes; `python -m cafe.receipts stamp FILE` stamps one that has been checked (look-ahead L0, M-35)."
- RUNBOOK/README sentence: after the `python -m cafe.cfd` lines in README: "The files carry a stamp; one made before the stamp, or crosscheck.json, is stamped with `python -m cafe.receipts stamp FILE` after you have looked at it."

## Adversary round on the L0 changes (two findings proved, both fixed at the shared place)

### M-25 regression: a server that answers a range with `Content-Range: bytes a-b/*` crashed `cdf1_header` with a bare ValueError
- Cause: `_ident` took `int()` of the text after the last `/`; `*` is a legal "total unknown". Since the identity check, every ranged read built an identity, so a server that worked before (nothing asked for its identity) raised a ValueError, which the retry loop does not catch.
- Change, in `cafe/pm/env/remote.py`: `_ident` (the one parser of Content-Range; `_read_ident`, `_probe` and `download`'s resume test all go through it) returns total -1 when the total is not a number (also a reply with no `/`). The piece reads (`cdf1_header`, `cdf1_read`, `bathy._rows`, `RemoteFile` blocks) compare identities as before, so such a server works as it did at 9b8eea6; the ETag and Last-Modified are still compared when it sends them. `_probe`, the only place that needs the size (`size`, `RemoteFile.n`, `download`'s `total`), raises ConnectionError "server does not state the file size" for -1 instead of handing a size of -1 on. In `download` a `/*` reply to a resume is a mismatch with the probed total, so it goes to `_probe` and ends in the same ConnectionError.
- Callers checked: `_read_ident` (identity -1 compared with -1), `_probe` (guard), `download` line 227 (compares with the probed total, which is never -1), `size`, `RemoteFile`, `cdf1_header`, `cdf1_read`, `bathy._rows`. No other parser of Content-Range exists in `cafe/` (grep). A 416 reply is `bytes */n` and never reaches `_ident` (`_open` turns it into FileNotFoundError).
- Tests (`tests/test_remote.py`): `test_r12_l0_m25_a_server_that_states_no_total_still_serves_the_header_and_the_reads_that_need_no_size` (both CDF formats, header and a variable read equal the local ones, `hdr.ident == (-1, {})`) and `test_r12_l0_m25_a_server_that_states_no_total_is_a_connection_error_where_the_size_is_needed` (`size`, `RemoteFile`, `download`). On the unfixed tree (e00a75b) all five fail with `ValueError: invalid literal for int() with base 10: '*'`.
- DECISIONS row: "`remote._ident` reads the total of a ranged reply's Content-Range and gives -1 when the server does not state one (`bytes a-b/*`) or it is not a number. Reads of pieces (`cdf1_header`, `cdf1_read`, GEBCO rows, `RemoteFile` blocks) go on and compare the identity as before, with the ETag and Last-Modified where the server sends them; `remote._probe`, which `size`, `RemoteFile` and `download` need the size from, raises ConnectionError 'server does not state the file size'. A total that is not a number was a bare ValueError that the retry loop did not catch. (amends the M-25 row; look-ahead L0 adversary)"
- CHANGELOG: "A server that sends `Content-Range: bytes a-b/*` is read for CDF headers, variables and GEBCO rows as before the identity check, and `size`, `RemoteFile` and `download` refuse it with a ConnectionError naming the missing size, not a ValueError (look-ahead L0 adversary, M-25)."

### M-33: the printed update command did not quote the mission or the golden-mission name
- Cause: only the golden path went through `shlex.quote`; `--mission {mission}` and `--golden-mission {name}` were pasted raw, so a path with a space was three words and a `;` ran the rest as a second command.
- Change, in `cafe/pm/acceptance.py`: `update_command` quotes `mission` and `name`. Two siblings of the same defect, found by grep for the flags: the refusal text of `golden_refusal` ("add `--golden-mission NAME`") and the `command` field `_golden_record` writes into a golden. Both quote now. For every name that needs no quoting (the demo's `missions/tepex_c_demo.yaml`, `ci_fixture`) the text is byte for byte what it was, so the shipped golden and the demo's printed text do not move. This replaces the line "Not changed: the `command` field inside a written golden" in the M-33 section above for the mission part.
- Callers checked: `check_golden` (four messages, `cmd` built once), `golden_refusal` (also called by `check_golden`'s update branch; its text is only printed), `_golden_record` (the field is not compared: `summary` and `source` are). The existing tests that read the advice through `shlex.split` and run it back through `check_golden(update=True)` pass unchanged.
- Test (`tests/test_acceptance.py`): `test_r12_l0_m33_the_mission_and_the_name_in_the_printed_command_are_one_word_each_whatever_they_hold`, three cases (space, `;`, a quote and `$(`): the printed command and the refusal's advice split into one word each, the text holds `shlex.quote(mission)` (so a shell sees no `;` or `$(`), and the words followed through `check_golden(update=True)` write the golden. On e00a75b all three cases fail.
- DECISIONS row: "Every word of a printed command that is ours to choose is `shlex.quote`d: `acceptance.update_command` (mission, golden path, golden-mission name), the `golden_refusal` advice and the `command` field of a written golden. A mission path with a space, or with `;`, was split or run as two commands when pasted. (amends the M-33 row; look-ahead L0 adversary)"
- CHANGELOG: "acceptance: the mission and the golden-mission name in the printed update command are shell-quoted (look-ahead L0 adversary, M-33)."
