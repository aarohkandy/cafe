## 1. A wording edit of config/assumptions.yaml failed every kept run's audit

Code. The stage-3 ledger recorded `config/assumptions.yaml` with the sha-256 of its bytes, so any edit, including a reworded `why` or `replace_with` that no stage reads, was `AUDIT FAIL ... input ... changed since the stage ran` for every kept run (and made `ledger.done` rerun stage 3 on a resume). Now `Ledger.input_values(path)` records such a file by `ledger.values_sha256`: sha-256 of the parsed mapping with the fields in `ledger.PROSE_KEYS` (`why`, `replace_with`) left out, read through `config.read_yaml` (the reader every stage uses). The input carries `values_only: true`, and `ledger.input_sha(i, f)` is the one place that compares a file input with what was recorded: `ledger.done` and `audit._stage_problems` both call it (they each had their own `sha256(f) != i["sha256"]`). A value, a unit, a key, an added field or a damaged file still changes the hash (a file that cannot be read as a mapping hashes to "", which no recorded hash equals). `pipeline_windows.run` records the file with `input_values`; `stage1/res.pkl` stays a byte hash.
Why the whole file is hashed by values and not by the `stage3.*` keys only: stage 3 reads other keys through code the ledger cannot list (`subgrid.*` and `env.sigma.*` through `GriddedEnv`, `bathy.*`, `tao.*`, `dtmb5415.*`); every one of the 101 entries is `{value, unit, why, replace_with}`, so the two prose fields are the only part that no reader uses.
Callers checked: `ledger.done` (resume), `audit._stage_problems` (the only comparison of a file input's hash); `report.py` prints a recorded `sha256` and compares nothing; `credibility.Facts.problems` counts what `ledger_problems` returns (fewer problems after a wording edit, the same after a value edit). `Ledger.input` is unchanged, so every other input (platform files, `radios.yaml`, `modems.yaml`, `mission.yaml`, `plan.json`, the JSON outputs) is hashed as before.
Sweep, siblings of the same defect: the other whole-file hashes in the ledgers are of files whose text a stage does read (a platform file's provenance text is checked by the hangar stage; the link tables are read whole; the JSON files have no prose-only field), so a wording edit of them is rightly a change. `config/assumptions.yaml` is the one file with a field no stage reads.
Not done, and why: a ledger written before this change holds the byte hash and cannot be told from one that records a real change, so q11, q12, q12la and q13 still print `AUDIT FAIL ... assumptions.yaml changed since the stage ran` (measured below). Turning that into a note for a run that is not the newest would also hide a real value edit (`stage3.fea_min_s` 8.0 to 68.2 in L0 is one) from the audit, which is the check's job. Only a rerun cures them (DECISIONS 515 says the same for added keys).
Measured on this tree (read only, `python -m cafe.pm audit /data/runs/<run> --ledgers-only`, orca): q13, q13la, q12la, q12 and q11 each print `AUDIT FAIL: <run>: stage stage3: input /app/config/assumptions.yaml changed since the stage ran` and `audit: 1 problem(s)` (it is the only problem line; q11 still has its old-run notes on stderr). P-R13L2-2 holds the same.

## 2. The demo's emulator design depends on the machine's speed, and the comparison read it as movers

Code. No change to the pipeline. `s_emulator` kills before a variant once the variants have spent the stage's share; that is the design (DECISIONS 288: "the kill before a variant stays the only enforcement", a look-ahead from measured seconds would make the count depend on the clock as well), and the report and the ledger already say how many variants ran (`run_note`, `design.json` `killed`, `variant_wall_s`). What failed was the comparison, which the finding names: `review/round_13/q13cmp.py` printed 190 leaves of `report.json`, 69 of `flip.json` and 27 of `design.json` as movers with nothing to say why. It now prints, first, `## variants run: A n of m run (killed: ...); B n of m run; COUNT DIFFERS ...` (from `emulator/design.json`), and when the counts differ it lists the leaves that follow the count apart, tagged `[load-dependent]` (every leaf of a file under `emulator/`, and in other files the `/emulator/` node, the `/fix/` nodes and `/machine/timing/variants/`), and counts them apart from the leaves that differ ("N (and M load-dependent: ...)"). The script is now functions with a `main` guard so a test can import it; the comparison it makes is the same.
Measured, read only on orca, the new `q13cmp.py q13la q13`: the first line reads `q13la 5 of 6 run (killed: ... before variant v5 of 6); q13 6 of 6 run; COUNT DIFFERS`; of the 470 json leaves that differ (design 27, flip 69, hold-out 20, credibility 7, report 190, the ledgers and the rest), 209 are tagged `[load-dependent]` and 261 stay in the list (provenance, config-hash ids, wall times, the credibility count that 681 moves); `stage1/res.pkl` and `stage1b/res.pkl`: 0 arrays differ, as before.
Not done, and why: the share (240 s on the quick budget), the variant cost and the kill are unchanged. The first five variants take 228 to 258 s of the 240 s on orca, so a 5 to 10 % slowdown still drops one; raising the share or lowering the cost moves `plan.json` and the demo's printed budget, which is the owner's decision (P-R13L2-1).
Callers checked: `q13cmp.py` is run by hand (`python q13cmp.py A B`) and by nothing else (`grep` over the repo); its output for runs with the same variant count is the old output plus the first line.
