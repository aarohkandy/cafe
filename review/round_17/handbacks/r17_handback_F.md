### S-2 `keep_mode` removed; one implementation
- `atomic.keep_mode` is gone. The two callers that cannot use `write_with` (a part that grows over several calls; a file a child writes by name) use `atomic.replace_from(src, p, follow_symlinks=False)`, **a rename, no copy** (the lead's second change: the first version copied the finished part through a second temporary, doubling the space and the IO of a part on a disk that is 97 % full). The link and mode rules are written once, in a new helper `atomic._target(p, follow_symlinks)` that `_replace_through` and `replace_from` both call: resolve (a loop of links is ELOOP, a dangling link is not), refuse a link at `p` (ELOOP) unless `follow_symlinks`, and return the nine permission bits of an existing regular file (None for a new name or a non-regular file). `replace_from` opens `src` with `O_NOFOLLOW` (a link as the source is ELOOP), `fchmod`s that descriptor with those bits, then `os.replace(src, p)`: `p` has `src`'s inode, `src` is gone, a failed call leaves `src`. Never setuid, setgid or sticky, never a mode read from a link's target.
- **What `_replace_through` did with special bits** (stated as asked): it set `S_IMODE(os.stat(p).st_mode)` (0o7777) on the new file, so an existing file with setuid, setgid or sticky kept them on a new file owned by the writer. Now `& 0o777`: the nine bits only. No widening: the bits kept are the ones the file had. `os.stat` there follows links, but `p` is either `realpath`-resolved (follow) or refused when a link, so it is the file itself.
- Tests: `test_r17_m13_replace_from_moves_a_finished_file_by_the_writers_rules` (mode kept, umask's mode for a new name, src gone, link refused), `..._replace_from_is_a_rename_the_file_at_the_name_is_the_sources_inode` (the inode test), `..._replace_from_follows_a_link_only_when_asked_and_a_loop_is_eloop`, `..._replace_from_never_widens_from_a_links_target_or_takes_special_bits` (setuid dest gets 0o755; a link as source refused), `..._the_target_of_a_replace_that_is_not_a_regular_file_has_no_mode_to_keep`, `..._the_mode_kept_is_the_nine_permission_bits_never_setuid_setgid_or_sticky[0o4755|0o2755|0o1777]`, and the two mode tests of download and `_fetch_part`.
- `test_config.py::test_r15_config_write_text_is_the_atomic_writer...` pins atomic.py's imports: unchanged, `{json, os, pathlib, stat, uuid}` (the copy version had added `shutil`; the rename needs none, so it is still the standard library only and no pin moved for it).
- DECISIONS: "921. `cafe.atomic` keeps the nine permission bits of an existing file, never setuid, setgid or sticky (it kept 0o7777); the link and mode rules are one helper, `atomic._target`, shared by `_replace_through` and `atomic.replace_from(src, p)`, which renames a finished file onto `p` (no copy: a part of a GOFS or TAO file is large and the disk is 97 % full) after putting those bits on it through an `O_NOFOLLOW` descriptor and refusing a link at `p`. Replaces the bare `os.replace` in `remote.download` and `hycom._fetch_part`." CHANGELOG line likewise.

### S-3 lock file and the unlocked download
- `store_lock` opens with `O_NOFOLLOW | O_CLOEXEC`: a link planted at the lock's name fails the open (ELOOP, an `OSError`), the block runs unlocked and its target is neither made nor opened. It now yields a bool: True when the lock is held (also for the thread that already holds it), False when not (no fcntl, a directory that cannot be written, a link at the name). Every existing `with store_lock(...):` is unchanged (they take no `as`).
- `download`: when the lock is not held it uses a part of its own, `atomic.tmp_name(path)`, not resumed, removed with its `.id` in a `finally` whatever happens (a failed or pin-mismatched download included).
- Callers of `store_lock` checked (audit.py:90 `create=False`; pipeline.py:184, 451 (`_shared_store`), 1050, 1071, 1110; surface.py:66, 134, 226; tests): none changed. The documented "no lock where the directory cannot be written" (DECISIONS 883, 911) is kept for all of them: a store nobody can write has no builder, and a link at the lock name now gets the same unlocked behaviour as an open that fails. Only `download` reads the new flag. Not done: the other callers do not refuse on a planted link (they run unlocked); their stores are built under unique temporaries since round 16.
