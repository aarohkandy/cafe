## 1. platforms/modems.yaml and radios.yaml were in no stage ledger (an edit of either was invisible to audit)
- Root: `comms._yaml` is the one reader of the two link tables, and `s_hangar` (the stage that hashes the files the later stages read) recorded only the vehicle platforms. Fix in the one place: `comms.PARAMETER_FILES = ("radios.yaml", "modems.yaml")` names what `comms._yaml` reads, and `pipeline.s_hangar` records each as a hashed ledger input (`L.input(comms.PLATFORMS / name)`). Hangar is the right stage: a stage that reruns makes every later stage rerun (`pipeline.run`, `redo`), and every later ledger chains to it, so one input there covers stage 1, stage 1b, the emulator variants (they call `stage1.run` with no ledger) and the report. `stage1.run` was not used: `whatif` calls it without a ledger, so it would leave the emulator uncovered.
- Callers checked: `comms._yaml` (radios at comms.py 143, 161, 431 and stage1.py 268; modems at 220, 235, 243, 258, 345) all read these two files; no other file in `platforms/` is read through it. `config._registry` reads the same two files for the loader's checks, which run before any ledger. Older ledgers (q10lb, q11, the runs of rounds before) do not list the two files, so `audit` of them is unchanged (a ledger is judged by the inputs it lists), and `ledger.done` of a finished stage reads only its listed inputs, so no resume of an old run reruns. A new run's hangar ledger lists two more inputs; tests that read hangar inputs by name (`tests/test_pipeline.py::test_hangar_lists_every_platform_file...`) still pass. The L0 pin of the four vehicle platform files is untouched.
- Tests (`tests/test_pipeline.py`): `test_l1_r11_the_hangar_stage_hashes_the_two_link_tables_every_link_verdict_reads`; `test_l1_r11_an_edit_of_modems_or_radios_after_the_hangar_stage_is_a_problem_of_the_audit` (runs the stage on a copy of `platforms/`, edits each file, expects `audit.ledger_problems` to say "input ... changed since the stage ran"); `test_l1_r11_every_yaml_the_link_models_read_is_one_the_hangar_stage_records` (greps `comms.py` and `stage1.py` for `_yaml("<name>.yaml")` and compares with `PARAMETER_FILES`, so a third table read the same way fails here).
- DECISIONS row text: `platforms/radios.yaml` and `platforms/modems.yaml`, the two tables every link verdict reads through `comms._yaml` (anchor margin, ambiguity band, valid-range factor, radio power and sensitivity), are hashed inputs of the hangar stage (`comms.PARAMETER_FILES`), like the vehicle platforms (461): an edit after a run makes `audit` say "input ... changed since the stage ran" for that run, and a resume reruns hangar and every stage after it. Runs made before this row (q10lb, q11 and earlier) did not record them and cannot be told of such an edit; they are not rewritten (588). Amends L0's note that `modems.yaml` is not a ledger input: from this row it is, for new runs, so an edit of either file is a deliberate act that says in DECISIONS which runs are re-run.
- CHANGELOG line: Fixed: an edit of `platforms/modems.yaml` or `platforms/radios.yaml` after a run was invisible to `audit`; the hangar stage now hashes both as ledger inputs (round 11 look-ahead L1; `tests/test_pipeline.py::test_l1_r11_*`).
- Not verified: the finding said modems.yaml appears in the emulator ledger of q11; I did not check q11's ledgers (not on this worktree), and it does not affect the fix.

## 2. worker_setup.sh refused to re-run on a worker it already filled
- Root: the 25 GB check ran unconditionally before the idempotent steps, but the figure is what a fresh install needs; on a finished worker the install has used it. Fix in the one place (`bin/worker_setup.sh`, before the check): the check runs only when the worker does not already hold the `cafe-pm` image and all of `work/cafe/pmdata/{bin,dtmb5415,bathy,tao,cache,ocean}` and `work/cafe/data` (the dirs the rsync lines fill). When it does, the script goes on to the install, load and rsync steps, which are idempotent (rsync copies only the difference). The header text says so.
- Callers checked: nothing calls `worker_setup.sh` but a person (grep of `bin/`, `docs/`); `orca_setup.sh` and `orca_ready.sh` have their own checks. A fresh machine, a machine with docker missing (the inspect fails) and a machine missing any one of the seven directories or the image still get the 25 GB check: the tests below show it for each.
- Ceiling: a first run that was interrupted after the image loaded and every directory was created (rsync makes the directory first) counts as finished, so a re-run on a full disk skips the check and the rsync itself fails loudly if the disk fills. Measuring the missing bytes would need the size of the source on homebase; not done.
- Tests (`tests/test_runners.py`): `test_l1_r11_worker_setup_run_again_on_a_finished_worker_with_less_than_25_gb_free_goes_on_to_top_it_up` (24 GB free, complete worker: exit 0 and the rsync runs); `test_l1_r11_worker_setup_still_checks_the_25_gb_when_the_image_or_a_data_directory_is_missing[...]` (8 cases: each of the seven directories and the image missing, 24 GB: exit 1 with the STOP line and nothing copied). The existing `test_r11_m19_*` tests pass unchanged.
- DECISIONS row text: `bin/worker_setup.sh` asks for 25 GB free only of a worker that does not yet hold the `cafe-pm` image and the seven data directories it copies (the install used that space; the header said "Re-running is safe", and the check made a re-run of a finished worker on a nearly full disk exit 1 before any top-up). A worker with both is not asked, and the rsync steps run as they did. Option kept out: measuring the bytes still missing (needs the source size from homebase). Amends 557's M-19 rule only in when it applies.
- CHANGELOG line: Fixed: `bin/worker_setup.sh` stopped with "25 GB needed" on a finished worker with less than 25 GB free; the check now applies only when the image or a data directory is missing (round 11 look-ahead L1).
