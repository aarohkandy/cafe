## M-15 `parse_cdf1` trusts a server's header

Change (`cafe/pm/env/remote.py`): the checks sit in the shared reader. `_Buf.take(n)` refuses `n < 0` and `n > MAX_ITEM` (64 MiB) before fetching anything; `_Buf.count()` (a count or length that must be >= 0) is used for every length, count, dimension size and dimension id; `_Buf.kind(want)` checks a list's tag is 0 or the expected one (and that an absent list has count 0); `_Buf.type()` refuses an unknown type code; a name that is not UTF-8, a dimension id outside the list, a negative shape (a streaming record count of -1 included) and a negative `begin` offset are each a `ValueError("damaged NetCDF header: ...")` saying what and at which byte. `cdf1_header` prefixes the file or URL (`<file>: damaged NetCDF header: ...`, and the same for "not a NetCDF classic file"). `cdf1_read` refuses a record number outside `0..nrec` for a record variable (`IndexError`, like the existing `rows` check; a non-record variable ignores `rec`) and multiplies shapes with `math.prod` (exact, no int64 wrap-around). A header that ends early is still `EOFError` and the identity `ConnectionError` is untouched: neither is caught.

Real headers (the lead asked for a real umwmrst header from the demo's cache): the demo's cache on orca holds only the derived zarr stores (`pmdata/cache/tepex_c_demo/orca/*.zarr`, `derived.zarr`), no raw CDF-1 file. So the real headers were read live, read only, with `remote.cdf1_header` from orca.atmos (a few range GETs of at most 64 KB, nothing written), after the change:
- `umwmrst_2023-03-01_12:00:00.nc`: the file is 2,517,132,616 bytes, **the header is 820 bytes**, 7 variables, the largest single field 20 bytes. (merged.md says the cap "must pass the real 2.5 GB restart header": it is the file that is 2.5 GB, not the header.) It parsed.
- `umwmout_2023-03-01_12:00:00.nc`: 127,737,904 bytes, header 7,708 bytes, largest field 59 bytes, `nrec` 1; parsed.
The cap is about 3 million times the largest real field; a 64 KB first read covers both whole.
Found while doing it (P-R13C2): `vsize` is an unsigned 32-bit number in the format, `parse_cdf1` reads it signed, and the real restart variable `F` (2,434,872,320 bytes) reads -1,860,094,976. (Second pass: `vsize` is now read unsigned, which is the format; see the second pass below.) A test builds a header with a 2.4 GB `vsize` and expects it to parse.

Callers and what could break: `orca.py` 168-227 (`umwm_grid`, `umwm_hour`, `spec_points`, `spec_hour`) are the only callers of `cdf1_header`/`cdf1_read` in `cafe` and `bin`; none passes `rec` (so the new record check cannot fire there), all read the two real files shown above. Tests: `tests/test_remote.py::test_r13_m15_*` (12 hand-built byte strings, the early-end `EOFError`, the file name in the message for a local and a URL file, the 1 MiB attribute below the cap, the 2.4 GB `vsize`) and the changed `test_record_index_past_the_end` (it expected `ConnectionError` or `FileNotFoundError` for a record past the end, and had nothing for -1; it now expects `IndexError` with the record and `0..nrec`, and the non-record variable still reads; this is a stricter assertion, not a weaker one).

## Second pass (after the adversary), commit on `r13-c`

Three problems proved by a 4000-mutation fuzz of `make_cdf` headers and a NaT probe, fixed at the root; P-R13C3 has the evidence.

**M-15, vsize (the finding's own symptom, `OSError` Errno 22).** `parse_cdf1` read `vsize` with the signed `i4`. It is unsigned in the format, and the sum of the record variables' `vsize` is the record size, so one damaged top byte made `recsize` -16777168 and `cdf1_read` seek to a negative offset. Fix: `vsize` is read as `>I` (the real `F` is now 2,434,872,320, not -1,860,094,976). No `vsize >= 0` check (vacuous now). A damaged vsize that stays positive (here 4.27 GB) is caught by the next item.

**M-15, a size the file cannot hold (`MemoryError`).** New `remote._fits(header, size)`: every variable's data must end inside the file (offset + bytes, and for a record variable offset + (nrec - 1) x recsize + one record's bytes); else `ValueError("damaged NetCDF header: v: its data would end at byte N, past the end of the file (M bytes)")`, with the path put in front by `cdf1_header`. `_header` calls it for a local file (`fstat`) and for a URL (the total of the first piece's identity; skipped when the server states none, -1). `cdf1_read` (the second place a size is used) now reads at most the bytes the file holds from the offset, so a header that no longer fits (the file shrank, or one built by hand) is the existing `short read` ConnectionError and allocates nothing; a negative offset or size is the same damaged-header ValueError. Real headers pass: read live from orca.atmos with `cdf1_header` (range GETs, nothing written): the restart (2,517,132,616 bytes, 7 variables, `F` ends at byte 2,517,132,616, the last byte of the file) and the output file (127,737,904 bytes, `nrec` 1) both parse. Callers: `orca.py` only (`umwm_grid`, `umwm_hour`, `spec_points`, `spec_hour`), on those two files. A file that is truncated but whose header is whole is now refused at the header, naming the variable and the byte, where before the read failed later with `short read`.

**M-32, NaT in hycom and tao.** `hycom.py` (joined GOFS parts, `_standardize` time coordinate, `_snapshot_times`) and `tao.py` (`_coverage`, `_series`, `wind_gap`) now use `environment.seconds`, which refuses NaT. `hycom._snapshot_times` still returns `[]` on that ValueError (it already caught ValueError: "the reader names it"), and `ingest_lab_hycom` then raises `1 of 1 time stamps are NaT` from the reader. In tao a new `_epoch(ds, path)` puts the file name in front (`x.nc: TIME: 1 of 6 time stamps are NaT`); `fetch_tao` catches the ValueError of `_coverage`, records `time_start`/`time_end` as null (nothing reads them) and lets `_series` mark the file unusable (`man["unusable"]`) so another deployment is picked, exactly as for a missing QC variable; `unusable_selected` lists it for a cache built before. Not changed: `Axis` still accepts any finite value, so a store written *before* this fix with -9.2e18 first would open; the demo's does not have one. The GOFS-parts line (`hycom.py` joined time) is changed for consistency but a NaT cannot reach it (the inner join drops that step and "N GOFS steps are missing" is raised first), so it has no test of its own.
