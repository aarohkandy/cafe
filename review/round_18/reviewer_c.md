## Findings

### C-1. The 'becomes' line of the fix table names the whole run's verdict beside the same-members P(fail), and the search targets the whole-run verdict
severity: minor
lane: statistics, honesty
where: cafe/pm/report.py:1413-1418 (`_fix_html`: `before` is `sm['p_fail']` on the same members, but the badge pair is `_badge(f['verdict_before'])` to `_badge(b['verdict'])`); cafe/pm/whatif.py:773 (`want` from `base["verdict"]`, the whole run's) and :828 (`verdict=base["verdict"]`)
reproduction: `x_c18/fixline.py` (orca, 2 CPUs, about 90 s): `flip_search` for glider_eq with the base run's real flags and the whole-run verdict label set to "NO-GO" (the demo flips nothing, so no real run prints this line; the label is the only synthetic part) renders: "deploy 6 h later ...: P(fail) 0.1562 on the same 32 members becomes 0.125 (0.0574 to 0.251, Wilson interval (Stage 1)), NO-GO to MARGINAL (Stage 1, n = 32 members); not distinguishable from the baseline". The 0.1562 is MARGINAL on its own members (`fix.same_members.verdict` = MARGINAL in the same dict), yet the pair reads NO-GO to MARGINAL, and the row is accepted as "a fix" because `want` came from the whole-run NO-GO. By reading: a whole run at 26 of 64 failures (NO-GO, 0.406) whose first 32 hold 12 (0.375, MARGINAL) and a candidate at 11 of 32 (MARGINAL) prints "NO-GO to MARGINAL" for a change that is 12 -> 11 failures on the same members and leaves the verdict where it already was on those members. In the q18 demo the two verdicts coincide (MARGINAL/MARGINAL, NO-GO/NO-GO, NO-GO/NO-GO), so nothing wrong is printed in q18.
why it matters: the headline of "What would fix it" is a verdict change; for a Stage-1 row the change that was measured is against the same-members baseline, whose verdict can differ from the whole run's. Only the "not distinguishable" tail guards it, and only when the interval contains the baseline.
wrong data: yes (when the verdicts of the whole run and of its first batch differ): the "NO-GO to MARGINAL" pair and the existence of a fix in the "What would fix it" line; not triggered by q18.

### C-2. `whatif` never reads the run's own plan: with another `--budget` (the default is quick whatever the run's budget) the "members of the full run" are not those members, and the documents say they are
severity: minor
lane: reproducibility, documentation
where: cafe/pm/__main__.py:300-345 (`ctx = pipeline.Context(a.mission, a.budget, ...)`; `ctx.plan` is this machine's plan for `--budget`, `run/plan.json` is not read), cafe/pm/whatif.py:738-739 (`measure` blocks of `plan["batch"]`), cafe/pm/stage1.py:475 (`sampling.lhs(M, ..., SeedSequence([seed, members[0]]))`: a hypercube per block of that size); docs/RUNBOOK.md:175 ("draws the members of the full run, so it is the answer of a rerun of the changed mission")
reproduction: `whatif --mission missions/tepex_c_demo.yaml --run /data/runs/q18 --budget ci --shift 6h --vehicle glider_eq` prints "glider_eq: MARGINAL (P(fail) 0.250) -> NO-GO (P(fail) 0.438) (0.258 to 0.635) [Stage 1, n = 16 ...]", with the note "the baseline shown above is the unchanged mission on the same 16 members as the answer; the report's own baseline, of the whole run's 64 members, is MARGINAL (P(fail) 0.234)". The same command with `--budget quick` gives MARGINAL 0.234 -> MARGINAL 0.172 (n = 64). The ci plan's batch is 16, q18's is 32 (`plan.json` batch 32), so block [0..15] is a hypercube of 16, not members 0 to 15 of the run's hypercube of 32 (the run's baseline on its first 16 is not 0.250). The pairing of candidate and baseline holds (both are measured on the same draws), so the printed pair is a true paired comparison, but the "members of the full run" claim does not. A run made with `--budget 4h` and a `whatif --run runs/x/4h` without `--budget 4h` (RUNBOOK:203 tells the user to give only `--run`) is in the same case, and when the two n happen to be equal (64 members, 2 blocks of 32 against one hypercube of 64) `answer` takes the report's own 64-member baseline as "same members" (`b.get("n") not in (None, s1["n"])` is False) although the draws differ (by reading, not run: needs a 4h run).
why it matters: the RUNBOOK promises the answer of a rerun with the run's draws; with a different budget the user gets other draws, a sign change as above, and no warning.
wrong data: no (every printed number is what it says; the claim in the document is what is wrong, and the baseline-on-the-answer's-members pairing is kept)
