### A-2. A huge integer in a JSON file is an uncaught OverflowError in the seed, in `vv.gci_value` and in `credibility.real_ok`; the seed accepts it into the CFD cache
severity: minor
lane: robustness
where: `cafe/_seed.py:16-17` (`_num`, used by `_vec` and the `rho`, `nu`, `L`, `resistance` checks) and `:50-57` (the `gci` check, `isinstance(g, (int, float))` only), `cafe/_seed.py:78` (`except (OSError, ValueError, RecursionError)`), `cafe/pm/vv.py` `gci_value` and `worst_gci` (`math.isfinite(g)` on an int), `cafe/pm/credibility.py:842-849` (`real_ok`, `conf_ok`); the repo's own helper `cafe/pm/config.py:359-365` (`finite_real`) says why: "json.loads gives a 400-digit literal as an int, and math.isfinite raises OverflowError on it", and catches it.
reproduction (`scratchpad/rev21_a/probe_a4.py`, orca, 2 CPUs):
```
_seed._num(10**400)                          -> OverflowError int too large to convert to float
_seed._checked("external", k, rho=10**400)   -> OverflowError
_seed._checked("external", k, gci=10**400 in all six directions)  -> ACCEPTED (returns the dict)
vv.gci_value(10**400), vv.worst_gci([0.1, 10**400]) -> OverflowError
credibility.real_ok(10**400), conf_ok(10**400)      -> OverflowError
issubclass(OverflowError, (OSError, ValueError, RecursionError)) -> False   (what `_seed.main` catches)
config.finite_real(10**400) -> False
```
So (a) `python -m cafe._seed` on a file with a 400-digit `rho`, `nu`, `L`, `resistance` or vector entry ends in a traceback instead of `NOT seeded <file> - ...` (nothing is written first, so no harm); (b) a 400-digit `gci` passes `_checked` (round 20's M-7 check asks "a number, NaN and inf included") and is written into the CFD cache under the real key, after which every `vehicle.build` that reads it raises `OverflowError` from `gci_value` (a cache entry that is poisoned until someone deletes it by hand); (c) a stored summary `conf` of 400 digits is an OverflowError from `conf_ok` and not the "summary edited or damaged" message that row 1035 promises for a count. `gci_value` also reads a numpy `float32` or `int64` index as `inf` (the `isinstance(g, (int, float))` test excludes both): unreachable today (`cfd.gci` returns a Python float), but the docstring says only NaN, None, text, a list or a bool read as inf.
why it matters: round 20's M-7 and M3 were about exactly this input class (a non-finite or odd number in a result file); the helper that handles it was in the repo and was not used by the three new readers.
wrong data: no. Fix: use `config.finite_real` (or catch OverflowError) in `_num`, `gci_value`, `real_ok`; and make the `gci` test in `_checked` refuse an int that is not finite as a float.

### A-4. The ambiguity band (+-6 dB) is narrower than the spread that round 20 measured in Bellhop's own answer, and no document says what that leaves outside the band
severity: minor
lane: physics, honesty
where: `platforms/modems.yaml:11` (`ambiguous_db: 6.0`, "BRIEF 2.8"); `cafe/pm/stage1.py:650-678` (`_acoustic`: Bellhop only for needed samples with `|Thorp margin| <= 6`); `docs/PHYSICS.md:832` ("outside the ambiguous band the two orders were identical"); `docs/RUNBOOK.md:189`; DECISIONS 1017; QUESTIONS_FOR_LAB 18a
reproduction (reasoning with the round's own numbers): the ray equations are reciprocal (`comms.acoustic_link` docstring), so if the true excess is T, the two directions give T + e1 and T + e2. Round 20 measured |e1 - e2| up to 26.5 dB (17.8 dB on one profile) at ambiguous samples, hence max(|e1|, |e2|) >= 13.2 dB: the Bellhop excess that is added to the Thorp TL can be wrong by more than twice the band. A sample whose Thorp margin is +8 to +19 dB (outside the band, so never refined) can therefore have a Bellhop-quality margin of the opposite sign, and a Thorp margin of -8 to -19 dB the other way; the fix makes the printed number order-free for samples inside the band and says nothing about the samples outside it. "Outside the ambiguous band the two orders were identical" is true only because no Bellhop runs there, and reads as reassurance.
why it matters: the verdict of an acoustic link near a shadow or duct is decided by Thorp wherever the Thorp margin is more than 6 dB from 0, and the new text says the number is conservative; the one place that is not conservative (a Thorp pass 6 to 19 dB above the line) is the one the documents are silent on. I did not run a real Bellhop profile to size it (B's lane).
wrong data: no (an unstated limit, not shown wrong on any run; the demo has no acoustic link in range). Suggested: one sentence in PHYSICS 12.2 and QUESTIONS 18a that the band was chosen before the 26.5 dB spread was known, and what a wider band would cost (Bellhop runs).
