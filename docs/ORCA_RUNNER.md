# Running cafe jobs on orca (proot)

Orca has no docker, so `PM_RUNTIME=proot` makes `bin/pmx.sh` and `pm.sh` run the same job in the cafe-pm root filesystem under proot (`bin/proot_run.sh`). Without it nothing changes.
The worker setup is `bin/orca_setup.sh` (`docs/orca/README.md`). Nothing here contacts orca until the commands below are run.

Orca is shared, maybe on one account, so everything of ours stays inside `~/cafe-worker`: `~/cafe-worker/cafe` stands for `~/work/cafe`, `~/cafe-worker/logs` for `~/logs` (tmux's socket too). `bin/pmx.sh` and `pm.sh` refuse without the folder's owner marker and take `PMX` as `pm_` and a plain name (letters, digits, `_`, `-`) and `TM` as a plain name, on both runtimes, so `rsync --delete` cannot reach outside (`PMX=pmdata`, `data`, `pm`, `tmp`, `..` and `../x` are refused with exit 2; another agent's `pm_*` can still be chosen by mistake, and a per-agent suffix would be needed to prevent that); `pm.sh` also keeps one owning checkout for the shared `pm` directory (`pm.owner`, `PM_TAKE=1`); a job refuses to start with under 60 GB free on the shared disk.
A number or size that is pasted into the remote command line must be plain, else the runner exits 2 with nothing sent: `PM_CPUS`, `PM_THREADS` and `CAFE_MIN_FREE_GB` are whole numbers from 1 to 999999999 (`1.5`, `2,`, `2;x` and a number of 10 or more digits are refused by length, as K of the gate is; `CAFE_MIN_FREE_GB=0` switches the disk check off; DECISIONS 780, 809), `PM_MEM` and `PM_SHM` (docker) a whole number with an optional `k`, `m`, `g`, `kb`, `mb` or `gb`, `PM_STOP_GRACE` whole seconds, and `TM` and a gate tag are each 2 or more letters, digits, `_` or `-`, the first a letter or digit (`orca_gate.sh`, `proot_suite.sh` and `pmx.sh` refuse the same names, with nothing sent; DECISIONS 580). `bin/pm_checks.sh` holds the rules, one copy for `pm.sh`, `bin/pmx.sh`, `bin/orca_ready.sh`, `bin/orca_gate.sh`, `bin/proot_suite.sh`, `bin/proot_run.sh` (by hand on the worker) and `bin/orca_sync.sh`. A gate tag, and under proot a `TM`, may not end in `_s<digits>`, `_serial`, `_shares` or `_audit`: those are the names of the suite's own job logs in the one flat logs folder, and the sweep of an earlier run's logs would delete the log of a tag named like one (review round 10, M-23, M-28). On the `bin/pmx.sh` path the defaults are `PM_CPUS=2` and `PM_MEM=12g` (docker; `pm.sh`, the lead's whole-box path, keeps 8 CPUs and 28g): 12g is the least that plans the demo mission (M-31).

## Go (about a minute of the owner's part, then the copy)

1. Owner: run `bash orca_setup.sh` on orca, open the login link, add the `cafe-orca` entry to `~/.ssh/config` (`docs/orca/README.md`, "Connect").
2. `sh bin/orca_sync.sh <orca tailnet IP>` copies proot, the root filesystem (the cafe-pm image, flattened) and the data (about 18 GB) from homebase, through pipes. Run it again to resume a cut copy; with no part named it copies only what is missing and does not refresh a part that is marked done. The address must be an IP address or a host name (letters, digits, `.`, `-`, `:`): anything else exits 2 before anything is sent (`bin/pm_checks.sh` `pm_host`; review round 11, M-18, DECISIONS 610). A part is marked done only after it arrived whole (the archive's own status counts, every directory is checked on orca, and a named part that is cut has no marker until it is copied again). Name only `proot root pmdata data`: any other name stops the script before it touches anything. `root` is not replaced while a process of ours runs from it (stop the job, or `ORCA_FORCE=1`).
3. `PMX=pm_<you> PM_HOST=cafe-orca sh bin/orca_ready.sh` (default `pm_ready`; use your own `PMX` when another agent may run the check) is the go check, on 2 CPUs, about 5 min: the worker is complete, a job runs, parallel OpenFOAM works, what the code sees of orca's CPUs and memory, how busy the machine is, and nothing of ours changed outside `~/cafe-worker`, looked at to depth 2 of `$HOME` (a new or removed entry or a changed directory there; a file rewritten deeper down, a new entry four levels down and anything outside `$HOME` are not seen; its busy-process list names processes only, no accounts: review round 11, M-19, DECISIONS 611). Its start marker is `~/cafe-worker/.ready_start_<PMX>`. The account is shared, so its last step fails only for a changed path with a name of ours (`cafe*`, `pm_*`, `pmx_*`) and lists any other changed path as a warning (exit 0). It ends `orca-ready` (review round 10, M-30).
4. After the owner's go: `PM_HOST=cafe-orca PM_RUNTIME=proot PM_CPUS=<n> PMX=pm_<you> TM=<name> bin/pmx.sh <cmd>`, as on the burst VM. Choose `<n>` from the load the check printed.
5. The whole suite and the gate: `PM_TAKE=1 PM_HOST=cafe-orca PMX=pm_<you> bin/orca_gate.sh <K> <tag> [--cov]` from the checkout (next section; `PM_TAKE=1` because a fresh worktree is another checkout than the one that owns `pm_<you>`, and a second sync onto a directory with a running `TM=` job needs it too: DECISIONS 794). `bin/orca_suite.sh` (12 xdist workers under one proot; arguments are split on spaces, so it holds `-m "not network"` itself) stays for a few files; for the whole suite it is the slow way (P-12, P-13).

## When `bin/pmx.sh` refuses to sync (exit 1, nothing sent)

`rsync --delete` empties `~/cafe-worker/cafe/pm_<you>`, so `bin/pmx.sh` (and the gate through it) looks first, and each refusal says what to do:

- `STOP: ... belongs to <host:path>` is the owner marker: the checkout that last synced a directory is written to `pm_<you>/.pmx.owner`, and a sync from another checkout (a fresh worktree is one) would empty the first one's code under its job. Use another `PMX=pm_<you>`, or `PM_TAKE=1` to take the directory over. A directory with no marker is claimed by the first sync.
- `STOP: the job <tag> is still running in ...` is the detached job (`TM=<tag>`, which is also the gate's tag) of that directory: its tmux session is alive, and the sync is refused even from the owning checkout. Wait for it (`tmux ls`), use another `PMX`, or `PM_TAKE=1`. The directory is recorded in the session (`PMX_DIR`), so another directory that has since reused the tag does not hold this one; a finished job holds nothing. A foreground job (no `TM`) is not recorded.
- `PMX=pm_<you> is required` is the gate: it has no default directory. The command is `PM_TAKE=1 PM_HOST=cafe-orca PMX=pm_<you> bin/orca_gate.sh <K> <tag> [--cov]`, with `PM_TAKE=1` the first time from a new checkout.

## The suite and the gate: one proot per job

Every traced system call of a job goes through one single-threaded `proot`. Measured on orca (`stat` calls per second, seccomp acceleration on): direct 1 process 389,000, 12 processes 1,525,000; one proot 44,000 for 1 process and 76,000 for 12; 12 separate proots 293,000. So 12 xdist workers under one proot got 1.7 times one worker's system-call rate, and 12 proots get 3.9 times that of one shared proot. The first full suite (12 workers, one proot, `bin/orca_suite.sh`) took 77.6 min (2,918 tests) and two timing tests failed from it. Real pipeline runs are little affected (their work is computing, not system calls); this is about test runs.

`bin/orca_gate.sh <K> <tag> [--cov]` (from the checkout; `PM_HOST` defaults to `cafe-orca`; `PMX` is required, and `PM_TAKE=1` the first time from a checkout that does not own that directory (`.pmx.owner`; a fresh worktree is another checkout; DECISIONS 794); the tag rule above applies) syncs as `bin/pmx.sh` does and starts `bin/proot_suite.sh` detached in tmux session `<tag>` on orca (log `~/cafe-worker/logs/<tag>.log`, ending `rc=N`). `proot_suite.sh` runs K separate `proot_run.sh` jobs of 2 CPUs (K at most 16: 32 CPUs; 32 is orca's cgroup quota, `/sys/fs/cgroup/cpu.max` reads `3200000 100000`, while `nproc` prints 64, the host CPUs the container can see: the quota bounds K, so 32 jobs of 2 CPUs would be throttled; review round 12, M-36, DECISIONS 676), each one plain pytest process (no xdist, `-vv`, `-m "not network"`) over its own share of the test files, all at once; then the real-time tests (`audit.SERIAL_TESTS`) alone. Shares come from `python -m cafe.pm.shares`: every test file in exactly one share (a test file is `tests/**/test_*.py`, the `python_files` of `pyproject.toml`, which the shares read: pytest and the shares cannot disagree, and a `*_test.py` is collected by neither; review round 10, M-29), greedy by the file's time (the time of a real-time test, `audit.SERIAL_TESTS`, which runs alone, is left out) in the junit files of the tag's folder (`pmdata/shards/<tag>/`), or in the first suite's `pmdata/junit_91c9777.xml`, or by size. Each share logs to `~/cafe-worker/logs/<tag>_s<i>.log` (a failure has its name while it runs), the serial tests to `<tag>_serial.log`, each ending `rc=N`. A job passes only if its exit status and its junit file agree.

**Reuse one tag for every gate.** A new tag balances from the first suite's junit, whose per-file seconds are those of 12 workers sharing one proot and are far off: the first gate with a new tag (K=12, `--cov`) planned 3,399 to 4,537 s for every share, and the jobs took 15 s to 3,167 s, so nine of 12 were done within 20 minutes and the last 26 minutes ran on one job at 1.1 CPUs (P-21). The tag's own last run balances the next. Reuse a tag that was itself run with `--cov` for a coverage run: coverage doubles `tests/test_pipeline.py` (3,026 s against 1,498 s), so the balance of a no-coverage run is wrong for a coverage run.

With `--cov` each job writes its own coverage file, then `coverage combine`, `coverage json` to `/app/coverage.json`, then `python -m cafe.pm.audit --pytest-receipt`, which writes `coverage.receipt.json` (the sha-256 of the code and of `coverage.json`, written only here, after every job passed), and `python -m cafe.pm.audit --pytest-done` (ruff, mypy, the scans, the mutation record and the coverage gates; it fails without the receipt, or when a file under `cafe`, `bench`, `tests`, `platforms`, `config`, `missions` or `pyproject.toml` differs from what the suite ran on; a suite run by hand needs `--pytest-receipt` run by hand, after you saw it pass; DECISIONS 602, 634). `proot_suite.sh` removes an old `coverage.json` and `coverage.receipt.json` first (`bin/sync_filters` keeps both across syncs). It also removes, at the start, the logs `<tag>_s<i>.log` of this tag with `i` above K, left by an earlier run under the tag with a larger K (each ended `rc=0` and ended a wait loop on `rc=` at once; P-30, DECISIONS 532); the tag's other logs are not touched. The gate exits 0 only if every job and the audit passed, and names what failed (`FAILED: s2(rc=1) audit(rc=1)`); until `docs/mutation.json` exists (`make mutation`), `audit(rc=1)` for that one problem is expected. Stop it like any job: `tmux kill-session -t <tag>` (or TERM, INT, HUP to `proot_suite.sh`, which acts at once in the shares step and the audit step too: DECISIONS 799): every job gets TERM through its `proot_run.sh`. The tag log then ends `rc=143`, like a TERM to the script (P-26). Check `/proc/loadavg` first: the sum of CPUs over everything of ours must stay at 32 or below; jobs run with PM_THREADS=2: peak 12.6 CPUs at K=8, 18.3 at K=12.

Measured (2026-11-06, 3,277 tests, both with all tests passing): **56.4 min with `--cov` at K=12** (tag `proof1`; 3,277 passed, coverage cafe/pm 99.950 %), and **33.6 min without coverage at K=8** (tag `go1`; 3,270 in the shares and 7 serial). Later, 3,352 tests: **51.9 min with `--cov` at K=8** (tag `proof1`, `e06879c`, 2026-11-06; peak 12.9 CPUs; 3,352 passed, coverage 99.915 %). These are two different runs, not one number: coverage and K differ. The floor is `tests/test_stage3.py` alone, about 31 to 34 min without coverage, so K above 5 or 6 helps nothing without coverage and K=8 is a safe choice. A share costs about 10 s to start (imports, collection, the session fixtures of `tests/conftest.py`).

The recorder writes one disk note per dip (latched under the floor plus 40 GB, cleared at the floor plus 45 GB) and notes a rerun of a job under the same name again if it fails with the same counts (the state of a finished log carries its modification time; the first look after the change of review round 10, M-26, writes one extra note per failing finished log).

**Replacing the flight recorder** (`bin/orca_watch.sh`, tmux session `watch`): kill its session, then start it again in a separate step. The tmux server exits with its last session, and a new session started in the same command loses the race against that exit (`server exited unexpectedly`); nothing was recorded for about 2 minutes (P-22). Copy the new script to `~/cafe-worker/bin/` first, and do not touch a session that is not yours.

**A pytest worker that dies with `node down: Not properly terminated` and no traceback** was killed by a signal, and the signal is the thing to read: put `pytest_testnodedown(node, error)` in a plugin and print `node.gateway._io.popen.poll()` (a negative number is the signal; -13 is SIGPIPE, which a shell reads as rc=141). Round 13's five deaths under `-n 2` were SIGPIPE, not load or memory: `gmsh.initialize()` resets that signal to its default (P-R13A-2, P-R14A1, DECISIONS 760), so a process that had meshed in-process died at its next write to a closed socket or pipe; `cafe.fea._gmsh` now sets it back. A death with another number is a new finding. The gate does not use `-n` (one plain pytest per proot job, above), which is why it never saw them.

## Stopping a job

`ssh cafe-orca 'TMUX_TMPDIR=$HOME/cafe-worker/logs cafe-worker/env/bin/tmux kill-session -t <name>'` (or a TERM, INT or HUP to the `proot_run.sh` process) stops the job, removes its temp directory and ends the job's tag log with `rc=143` (the pane shell passes the hang-up to the job and writes its status; before P-26 the shell died first and the log had no `rc=` line, so a wait on `rc=` never ended; the job's own per-share logs always did): TERM to the whole job, KILL after `PM_STOP_GRACE` seconds (whole seconds, default 10, as `docker stop`; `pmx.sh` and `pm.sh` pass it on and refuse anything else). `kill -9` on the wrapper does not: the job keeps running under proot (find it with `ps -ef | grep cafe-worker/bin/proot`, stop it with `kill -TERM -<its pid>`, a process-group kill), and its `~/cafe-worker/cafe/tmp/run.*` directory stays until the next `proot_run.sh` start sweeps it, once the job has ended (a process that is only a zombie counts as ended). The same goes for an orca restart. `bash orca_setup.sh undo` refuses while a job of ours runs (stop it first), logs out of Tailscale before it stops the daemons and says if the logout failed; the owner then removes `orca-cafe` in the admin console. The sweep assumes one container at a time uses this home (it reads the pids in `run.*/.pids`).

## What is not the same as docker

- `PM_MEM` and `PM_SHM` are not enforced. `PM_CPUS` has no `--cpus` to land in, so `bin/proot_run.sh` keeps it itself (next bullet; `bin/pmx.sh` defaults it to 2) and also sets `CAFE_WORKERS` from it. `/work` is writable.
- Exit status. proot answers with the status of the last process of the job to end, not of the first (`sh -c "(sleep 3; exit 7) & exit 1"` gave 7), and a child that outlives the job, such as the resource tracker `multiprocessing` starts for spawned workers, exits 0: a failed pytest or pipeline run read `rc=0`. `bin/proot_run.sh` now runs the job inside a small `sh -c` that writes its status to the job's `/tmp` and exits with that (a job killed outright, or a full disk, leaves none: then a nonzero status from proot stands and a 0 counts as a failure, `proot_run: the job left no exit status`). `rc=N` in a log is the job's own, as with docker; an `rc=0` from before this change may be wrong for a job that spawned workers (DECISIONS 523).
- Two tests of `tests/test_runners.py` (the rsync sync ones) need `--no-perms` under proot on kernel 5.10 and do it themselves. Cause (probe, glibc 2.39): `fchmodat(..., AT_SYMLINK_NOFOLLOW)` fails with ENOENT, because glibc does it through `fchmodat2` (Linux 6.6 and later; 5.10 has none) or else through an `O_PATH` descriptor and `/proc/self/fd/N`, which proot does not translate. So any program in the image that sets modes without following symlinks (`rsync -a`, `cp -a`, `shutil.copytree(symlinks=True)`) fails the same way on orca; nothing in `cafe/pm` calls it (P-16).
- A job is pinned to `PM_CPUS` cores and its thread pools are sized to them (round 15, P-R14V5, DECISIONS 826, 827). There is no cgroup per job under proot, and a job's BLAS, OpenMP and XLA pools size themselves to the 64 CPUs `nproc` shows: one matrix product started 416 threads and kept 17 CPUs busy (P-20), and a JAX matmul loop of a `PM_CPUS=2` job ran at cpu time over wall time 32.1 on orca, the whole 32-CPU quota, until it pinned itself with `taskset` (1.82 once `bin/proot_run.sh` did it, measured 2026-11-11, `review/orca/PROBLEMS.md` P-R14V5). So `bin/proot_run.sh` runs the job under `taskset -c <PM_CPUS cores>` (the affinity is inherited by every process under proot) and sets `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` and `XLA_FLAGS=--xla_cpu_multi_thread_eigen=true intra_op_parallelism_threads=<n>` in the job's environment, `n` being `PM_CPUS` or, when set, `PM_THREADS=<n>` (the suite's jobs set both to 2). The cores are the least busy ones over half a second of `/proc/stat` (other people's load counts, ours too), each claimed with an atomic `mkdir ~/cafe-worker/cafe/tmp/cpu.<n>` holding the wrapper's pid and, once it runs, the job's, so the K jobs of a gate that start together get different cores. The claims are made one wrapper at a time, under `flock` on `~/cafe-worker/cafe/tmp/cpulock` (leave that file; without `flock` the job says so and claims unlocked). A claim is taken over only when neither pid is alive: a `kill -9` of the wrapper leaves the job running on its cores. The claim goes with the job (round 15, look-ahead L0). With fewer free cores than `PM_CPUS` the rest is shared with the least busy claimed ones and the job log says `no free core ... sharing`; the job log's first line says `proot_run: pinned to cores 3,5 (PM_CPUS=2), pools of 2 threads`. `PM_CPUS` at or above the CPUs the shell may use pins nothing; a worker with no `taskset` or `/proc/stat` runs the job unpinned and says so. `env OMP_NUM_THREADS=<n> ...` or `env XLA_FLAGS=...` in front of the command overrides a pool for one job. Pipeline runs now have pools of `PM_CPUS` threads where they had the libraries' own (amends DECISIONS 524: "a thread count can change the last bits of a sum" was the reason to leave them, and a job that takes the machine is the worse harm). Under docker `bin/pmx.sh` and `pm.sh` send the same four variables at `PM_CPUS` (the cgroup quota of `--cpus` leaves the pools at the host's CPU count).
- Memory is unguarded. Under docker `CAFE_WORKERS` is unset and the planner cuts the workers to what the cgroup memory holds; here `CAFE_WORKERS` is set, which `cafe/pm/budget.py` reads as an explicit choice: no memory cut, only a note in the plan when memory is short. So `PM_CPUS` must keep the sum over all running jobs at 32 or below (orca's cgroup), and the memory of all jobs together under 256 GiB is yours to watch; `proot_run.sh` warns when `PM_CPUS` is above 32. `par.memory_gb()` reads orca's cgroup through proot (`/sys` is the host's: 274.9 GB) and cuts it to the machine's `MemTotal` (270.2 GB; DECISIONS 519).
- TAO. Since review round 10 the TAO cache of the current selection rule is `<data>/tao/s2`; the first run after the update fetches it, which needs the network once (also on a machine that runs with `CAFE_OFFLINE`), and the older `<data>/tao/manifest.json` and files stay for the runs that read them. `bin/orca_sync.sh` and `bin/worker_setup.sh` copy the whole `tao` directory, so `s2` goes along from a machine that has fetched it (DECISIONS 571). That happens on the first copy of `pmdata`: a run of `orca_sync.sh` with no part named copies nothing once `pmdata.done` exists, so an `s2` fetched on homebase later reaches orca by naming `pmdata` (it copies all six directories again, about 13 GB, to move a few hundred MB) or by copying `tao` by hand (DECISIONS 610). `bin/worker_setup.sh` (for a machine reached through homebase, such as the deleted burst VM) checks for 25 GB free first, unless the worker already holds the `cafe-pm` image and its data directories; on a machine where the login is not yet in the docker group the first run adds it and stops with exit 1: log out of that login and run it again (DECISIONS 611, 636).
- `plan` and `run` note that `config/throughput.json` was measured on another machine (homebase's block) until `make bench` is run on orca; the planned stage-1 times are homebase's until then (review round 9, M-9).
- Kernel 5.10 and orca's cgroup (32 CPUs, 256 GiB, 64 MB `/dev/shm`) are the real limits; the temp directory is `~/cafe-worker/cafe/tmp/run.*` on the big disk, removed after the run.
- Open MPI runs with `PMIX_MCA_gds=hash`: without it every `mpirun` aborts at start under proot (rehearsed). If ranks later die with "Read -1, expected" add `OMPI_MCA_btl_vader_single_copy_mechanism=none`; the rehearsal did not need it.
